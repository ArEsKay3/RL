Investigated 2026-09-29. Every SWE-E2E v2 config.yaml carries a live-looking `effort_levels` block (top level, e.g. chain J: `low_penalty: 1, low_string: '{reasoning effort: efficient}', low_ub: 15000, low_weight: 0.1`). The chat template appends the literal string `{reasoning effort: efficient}` to low-effort-tagged turns (`chat_template.jinja:168`), and `EffortLevelsConfig`/`_apply_effort_shaping` (`nemo_rl/experience/rollouts.py:371-458`) implements a real length-based reward adjustment keyed on that substring: `length_reward = min(1, low_weight*(1-len/low_ub))`, blended into `orig_reward`.

**It never runs for these arms.** Full call chain, verified by direct grep (not inference): `_apply_effort_shaping` <- `_postprocess_single_nemo_gym_group` (rollouts.py:2599) <- `run_async_nemo_gym_rollout` usage at rollouts.py:2472, reached only from two places: `AsyncTrajectoryCollector._iter_rollout_groups` in `nemo_rl/algorithms/async_utils/trajectory_collector.py` (a third, separate "async_grpo" pipeline inside grpo.py, not SC), and the synchronous "compatibility API" wrapper at rollouts.py:2520-2571 (docstring: "drains run_async_nemo_gym_rollout... returning only after every row is complete" -- built for the old fully-sync ppo.py/grpo.py/sync_rollout_actor.py loops). `nemo_rl/algorithms/single_controller.py` -- the file that runs every SWE-E2E v2 arm (chain J, run A, chain K, chain M/N, chain P family, etc.) -- has zero references to `effort_levels`, `effort_config`, `_apply_effort_shaping`, `_postprocess_single_nemo_gym_group`, `run_async_nemo_gym_rollout`, or `AsyncTrajectoryCollector`. Checked `single_controller_utils/` for a parallel reimplementation too -- the only grep hit was a docstring false positive ("length and reward" in an unrelated metrics-aggregation sentence).

**Why:** `effort_config` and `reward_penalty_config` are literally sibling parameters on the same dead compatibility function (rollouts.py:2520-2571) -- this is the same class of gap already found for the -5 advantage/reward penalties (see [[swe-main915-penalties]]: "v2 arms never applied the -5 advantage penalties/reward_penalties; NeMo RL main does"), now independently confirmed for a second, unrelated mechanism. Both were probably wired for the old sync/async_grpo loops and simply never ported to SC.

**How to apply:** any SWE-E2E v2 arm's pass@1/length numbers should be read as NOT length-penalized by effort_levels regardless of what its config.yaml says -- the config block is fully populated and looks active but is dead weight on this pipeline. If asked whether swe_main915 (chain U/V/W, NeMo RL main) applies it, that needs its own check -- main's SC path is known to apply reward_penalties where v2 didn't, so effort_levels may differ there too; not yet verified.
