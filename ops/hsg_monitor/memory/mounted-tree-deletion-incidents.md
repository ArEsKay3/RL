Twice now a LIVE-MOUNTED nemo_rl checkout has had its package directories wiped while jobs were running against it, with no Claude session responsible.

2026-09-19 ~20:37 swe_dump/nemo_rl (plus Gym code). 2026-09-24 22:24:32 swe_replay_splice: 376 tracked files in nemo_rl (all of nemo_rl/algorithms including single_controller.py, nemo_rl/experience/foreign_rollout_source.py; only 1 .py left of 305) AND 1,641 tracked files in the Gym submodule. Both times .git survived, /runs and all checkpoints survived, and the deletion targeted package/source dirs only.

MECHANISM (confirmed 2026-09-24): the workspace is bind-mounted READ-WRITE into the container. launch_swe_dump.sh:131 and the splice launcher both set
  EXTRA_MOUNTS="${WS}:${WS},${SWE_BASE}/swe_e2e_corrected:...,${MINE}/runs:${MINE}/runs,${MINE}/persistent_cache:...,${HF_HOME}:${HF_HOME}"
with NO :ro on any entry and no --container-mounts override downstream. So anything running arbitrary shell inside the container - a SWE-agent sandbox or Gym - can unlink files in the live checkout. That is why both events hit a live-mounted tree and left .git and /runs alone.

2026-09-25: a near-miss worth recording as a CHECKING PROCEDURE, not an incident. The "Get Latest Main?" session committed a012970be to swe_915/Megatron-LM (partial port of MLM PR #7598, EOS detection when splicing the un-retokenized prefix) at 12:07:33 while chain S (swe_915 vLLM from scratch, masking off, 4006271, started 10:16:57) was running; chain T (swe_915 MINF from scratch, masking off, 4006272) started 14:21:36 after it. I flagged this as a split A/B pair and was WRONG: launch_swe_915.sh:142-145 gates the `EXTRA_MOUNTS` append that adds MLM_TREE behind `if [[ "${ENGINE}" == "minf" ]]`, so a vLLM arm never mounts the fork over the container's Megatron-LM at all, and the edited file lives in megatron/core/inference/text_generation_server/, which is MINF-only. chain S ran the container's stock copy throughout; chain T started clean on the fixed tree. No split.

**The generalisable rule, which does hold:** these workspaces bind-mount code trees live with no snapshot, so before treating two arms as a single-variable A/B, check every live-mounted tree's file mtimes and commit times against BOTH jobs' start times - AND check whether the mount is conditional (engine-gated here). The mixed-tree hazard is real for any arm whose worker restarts after a live edit, since Python holds the version it imported at startup while a fresh process reads the new one.

2026-09-26 THE SAME MECHANISM, USED DELIBERATELY: `ray.sub:262` passes `--container-mounts=$MOUNTS` (standard Pyxis bind-mount), which attaches at CONTAINER-START time, not at sbatch submit time; `launch_swe_main915.sh` also sets `USE_SNAPSHOT=0` explicitly. So a HELD job reads the tree as it exists when its srun steps finally launch, which means a fix committed after submission is picked up for free and no cancel/resubmit is needed. That is the useful half of the live-mount design - the same property that makes a mid-run tree edit or deletion dangerous (see the 09-19, 09-24 and 09-25 entries above) makes a held job self-updating. **When a fix lands after a job was submitted, check the mount mode before assuming a resubmit is required** - verified by the "Get Latest Main?" session for chain U (4023058) after commits 81cea49a3 + 13ef93615.
