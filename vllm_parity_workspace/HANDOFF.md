```bash

# fresh arm, new seed
EXP_NAME=<run-name> SLURM_PARTITION=batch_long SLURM_QOS=hero-res \
  SLURM_RESERVATION=sla_res_nemotron_sw_post WALLTIME=8:00:00 \
  bash launch_swe_vllm_parity.sh grpo.seed=<seed>

# resume an existing EXP_NAME from its last checkpoint (same command, no seed
# override needed — checkpoint_dir is derived from EXP_NAME and auto-resumes)
EXP_NAME=<run-name> SLURM_PARTITION=batch_long SLURM_QOS=hero-res \
  SLURM_RESERVATION=sla_res_nemotron_sw_post WALLTIME=8:00:00 \
  bash launch_swe_vllm_parity.sh

# chain follow-on segments without waiting for a wall (recommended — chain V

SLURM_DEPENDENCY=afterany:<previous_job_id> [...same as above...]

# 16-node smoke, 2 steps, short QOS
SMOKE=1 bash launch_swe_vllm_parity.sh
```

## Two traps that cost real time this project — read before editing the yaml

1. **Hydra validates CLI overrides against the YAML, not the Pydantic
   schema.** A key that exists only as a Python dataclass default is
   invisible to `a.b.c=value`; it needs `+a.b.c=value` unless some yaml in
   the config's `defaults:` chain already declares the key. Getting this
   wrong is silent until the job starts, then costs ~3 minutes and the queue
   slot — and on a chained arm, every queued segment dies the same way.
   `grep` the **target config's actual yaml chain** for the key before
   picking a form; don't reuse another tree's answer.
2. **Unquoted `off`/`on`/`yes`/`no` in a yaml is a YAML 1.1 boolean**, not a
   string. `token_ids: off` parses as Python `False`; a `Literal["off",...]`
   schema field then rejects it. If you add a bare on/off-shaped default to
   any yaml here, quote it (`token_ids: "off"`) or use a value that can't
   collide (`none`/`disabled`). Verify with `python3 -c "import yaml;
   print(yaml.safe_load(open('f.yaml')))"` before trusting an edit — that
   needs no cluster allocation and catches both traps in seconds.

Full incident writeup: search memory `hydra-override-plus-vs-plain`.

## What HSG has to change

Everything below is CMH-specific and must be re-pointed on another cluster;
nothing else in the launcher or configs is cluster-specific.

- `SWE_BASE`, `MINE`, `MY_HF_HOME` at the top of `launch_swe_vllm_parity.sh`
  (currently under `/scratch/fsw/portfolios/nemotron/projects/...`).
- `CONTAINER` — pinned to `rl-gym.63635108-zstd.sqsh` under `akamehra`'s
  containers dir. This is the same container the parity post-mortem was
  audited against; don't casually swap it, the staged `cutlass`/`quack`
  packages (below) are sourced from inside it.
- `SLURM_RESERVATION=sla_res_nemotron_sw_post`, `SLURM_QOS=hero-res`,
  `SLURM_PARTITION=batch_long` — CMH-specific scheduling. HSG needs its own
  equivalents or plain `SLURM_QOS=normal` with no reservation.
- **`parity_site/` must be re-staged** on first use on a new cluster:
  `sbatch tools/stage_parity_site.sbatch` copies CUTLASS DSL 4.5.2 and
  `quack` out of `/opt/gym_venvs/responses_api_models/local_vllm_model/.venv`
  inside the *same container image* — this only works because that venv
  ships both packages at matching torch/triton versions. If HSG uses a
  different container, check that venv exists first; if not, the packages
  need sourcing some other way (see `PARITY_BRANCH_REPORT.md`'s deployment
  note for why the Megatron policy-worker venv can't provide them itself).
- Megatron-LM mount target
  (`/opt/nemo-rl/3rdparty/Megatron-Bridge-workspace/Megatron-Bridge/3rdparty/Megatron-LM`)
  is a container-internal path, not cluster-specific — leave as is unless
  the container image changes.
- Checkpoints/dumps themselves do not move. To continue an arm on HSG,
  either point `RESULTS_DIR`/`PERSISTENT_CACHE` at a copy of the relevant
  `checkpoints/` directory (140 files + rolling per rung, ~368 GiB/rung
  before HF export strip) transferred off CMH Lustre, or accept restarting
  that arm from scratch on HSG with a fresh `EXP_NAME`.
